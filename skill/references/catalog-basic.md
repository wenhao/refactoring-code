# 手法目录：第一组重构（基础）

> 提炼自《重构（第二版）》第 6 章。括号内数字为原书页码，仅供人工溯源。
> 每条含：动机（何时做/何时不做）+ 做法（小步清单）。

## 6.1 提炼函数 Extract Function（106）
曾用名：提炼方法。反向：内联函数(115)。

**动机**：最常用的重构。判据是"**将意图与实现分开**"——需要花时间浏览才能弄清一段代码在干什么，就该提炼并以用途命名（不是长度、不是复用次数）。函数超过 ~6 行开始有味道；一行函数也可以。注释常常提示好名字。想不出更好的名字是不该提炼的信号；可以先提炼试试，不合适再内联回去。

**做法**：
1. 新建函数，以"做什么"命名（不是"怎样做"）。支持嵌套函数时先嵌套在源函数内（少操心作用域），以后再搬移函数(198)出去。
2. 复制待提炼代码到新函数。
3. 处理源函数作用域的变量：
   - 只读取 → 作为参数传入；
   - 声明在外但只被提炼段使用 → 把声明一起搬进来；
   - 在提炼段被赋值且只此一个 → 让新函数返回该值；
   - 被赋值的局部变量太多 → **先放弃提炼**，改用拆分变量(240)/以查询取代临时变量(178)理顺变量再来。
   - 源函数参数被赋值 → 先用拆分变量(240)改成临时变量。
4. 编译（如有编译期检查）。
5. 源函数中的原代码替换为新函数调用。测试。
6. 搜索其他相同/相似代码，考虑用以函数调用取代内联代码(222)复用。

要点：喜欢每个函数只返回一个值；要返回多个值时，更好的选择是换一块代码提炼，或返回记录对象。

## 6.2 内联函数 Inline Function（115）
反向：提炼函数(106)。

**动机**：函数体与名字一样清晰（非必要间接令人不舒服）；或有一群组织不合理的函数，先全部内联成大函数再按更好的方式重新提炼。

**做法**：
1. 确认函数不具多态性（有子类覆写则不能内联）。
2. 找出所有调用点，逐一替换为函数本体，每次替换后测试（不必一次完成）。
3. 删除函数定义。

遇到递归、多返回点、无法访问的中间对象等复杂情况 → 说明不该用此手法。复杂时逐行内联，用搬移语句到调用者(217)拆更细。

## 6.3 提炼变量 Extract Variable（119）
曾用名：引入解释性变量。反向：内联变量(123)。

**动机**：复杂表达式难以阅读，局部变量给一部分逻辑命名；也方便调试。若名字在更宽的上下文也有意义（如在类中），优先提炼成函数(106)而非变量。

**做法**：
1. 确认表达式无副作用。
2. 声明**不可修改**变量，复制表达式为其赋值。
3. 用新变量替换原表达式（多处出现则逐一替换，每次测试）。
4. 测试。

## 6.4 内联变量 Inline Variable（123）
曾用名：内联临时变量。

**动机**：变量名不比表达式本身更具表现力；或变量妨碍附近的重构。

**做法**：
1. 确认赋值右侧无副作用。
2. 先把变量变为不可修改并测试（确保只赋值一次）。
3. 逐一将使用处替换为右侧表达式，每次测试。
4. 删除变量声明。测试。

## 6.5 改变函数声明 Change Function Declaration（124）
别名：函数改名/修改签名。

**动机**：函数名与参数列表是"系统的关节"。好名字让用途一目了然（技巧：先写一句注释描述用途，再把注释变成函数名）。改参数能扩大适用范围、去除模块间耦合（如参数从 person 改成电话号码）。参数选对象还是细粒度值没有唯一正确答案，会随时间变化——所以会做这个重构最重要。

**简单做法**（调用者少/有可靠工具）：直接改声明 → 改所有调用者 → 测试。改名+增参分开两步做。遇到麻烦就回滚改用迁移式。

**迁移式做法**（调用者多/多态函数/已发布 API）：
1. 必要时先重构函数体，便于提炼。
2. 用提炼函数(106)把函数体提炼成新函数（暂起一个易搜索的临时名，如 `zz_` 前缀）。
3. 给新函数增/改参数（此步用简单做法即可）。可加引入断言(302)确认新参数被正确使用。
4. 测试。
5. 对旧函数用内联函数(115)，逐个调用点迁移。
6. 新函数改回正式名字。测试。

多态：每个实现版本都要提炼转发；继承体系只需在超类转发。已发布 API：新函数就位后暂停，旧函数标记 deprecated，等客户端迁移后再删。

## 6.6 封装变量 Encapsulate Variable（132）
曾用名：自封装字段/封装字段。

**动机**：数据比函数难重构（函数可留转发，数据没有转发机制）。先以函数封装所有访问，就把"重组数据"化为"重组函数"。作用域超出单个函数的**所有可变数据**都应封装；作用域越大越重要。公开字段即考虑封装。**不可变数据是更强的防腐剂**——不能改就无须封装更新逻辑。

**做法**：
1. 创建取值/设值封装函数。
2. 静态检查。
3. 逐一修改使用处改为调用封装函数，每次测试。
4. 限制变量可见性（如移入模块只导出函数）。无法限制时改名（如 `__privateOnly_xxx`）逼出残留引用。
5. 若值是记录 → 考虑封装记录(162)。

**封装值（更深一层）**：基本手法只封装最外层引用，管不住结构内部修改：
- 取值函数返回副本（`Object.assign({}, data)`；列表尤其常用）；
- 或用封装记录(162)的类阻改；
- 设值也可复制入参，防源数据变化引发事故。
- "侦测/阻止修改"通常是临时处置，随后去掉修改逻辑或提供正规修改函数。

## 6.7 变量改名 Rename Variable（137）

**动机**：作用域越广，名字越重要。动态类型语言可把类型编进名字（aCustomer）。

**做法**：
- 广泛使用的变量：先封装变量(132)再改名（改完通常保留封装，很少内联回去）。
- 函数内变量：直接改所有引用，测试。
- 常量/只读变量：**复制一份新名字**（`const newName = oldName`），逐一迁移引用，最后删旧名——无须封装即可小步完成。
- 已发布变量（外部代码库引用）不可用此重构。

## 6.8 引入参数对象 Introduce Parameter Object（140）

**动机**：数据泥团（一组数据项总是结伴穿过多个函数签名）。真正意义在于催生更深改变：识别出新结构后，围绕它的共用行为会浮现（如 NumberRange 的 `contains`），上升为新抽象概念。

**做法**：
1. 创建数据结构（倾向用类，方便日后放行为；尽量做成值对象——不提供修改函数）。
2. 用改变函数声明(124)给函数**新增**该结构参数（先不删旧参数）。测试。
3. 调用者逐个传入适当实例。每次测试。
4. 函数体内逐项用新结构字段替换旧参数，每替换一项测试，最后删除旧参数。

## 6.9 函数组合成类 Combine Functions into Class（144）

**动机**：一组函数形影不离地操作同一块数据（数据常作为参数传来传去）。类提供共用环境、少传参数、便于整体传递，还便于发现更多可搬入的计算逻辑。类 vs 变换(149)：**源数据会被更新 → 用类**（派生数据自动保持一致）；只读 → 皆可。倾向类胜过嵌套函数（后者难测试）。

**做法**：
1. 用封装记录(162)封装共用数据记录（还不是记录结构则先引入参数对象(140)组织成记录）。
2. 对每个函数用搬移函数(198)移入新类（参数已是类成员的从参数表去除）。
3. 处理数据的逻辑可先提炼函数(106)再移入。

好处体现为"统一访问原则"：客户端分不清 baseCharge 是字段还是计算出的值。

## 6.10 函数组合成变换 Combine Functions into Transform（149）

**动机**：把派生数据的计算收拢到一个变换函数中（输入源记录，输出填好派生字段的新记录），杜绝计算逻辑到处重复、难以寻找。命名习惯：返回增强后的原对象叫 `enrichXxx`；生成完全不同的对象叫 `transformXxx`。

**做法**：
1. 创建变换函数，先只**深复制**输入并返回。写一个测试确认原记录未被修改。
2. 挑一块派生计算逻辑移入变换函数，结果作为字段放进输出记录（复杂逻辑先提炼函数(106)）。测试。
3. 改客户端用新字段。
4. 对其余计算逻辑重复。

陷阱：源数据之后被修改会使变换结果不一致——可变环境下改用函数组合成类(144)；只读上下文（如展示派生数据）可安全使用变换。

## 6.11 拆分阶段 Split Phase（154）

**动机**：一段代码同时处理两件不同的事（如"计算商品价格"与"计算配送成本"），拆成顺序执行的独立模块，修改时只聚焦一个主题。线索：代码出现上下几段，各自使用不同的一组数据和函数。编译器（词法→语法树→优化→目标码）是典型。

**做法**：
1. 把第二阶段代码提炼成独立函数。测试。
2. 引入**中转数据结构**作为该函数的新参数。测试。
3. 逐个检查第二阶段函数的参数：第一阶段用到的（或虽在第一阶段用到但可搬的）移入中转数据结构，每次测试。第二阶段不该用的参数，把用它的结果提炼为中转字段，代码行用搬移语句到调用者(217)移出。
4. 把第一阶段提炼成函数（或变换对象），返回中转数据结构。测试。

完成后中转结构即两阶段之间的接口；多余的临时变量顺手内联。
