# 手法目录：处理继承关系

> 提炼自《重构（第二版）》第 12 章（`knowledgebase/book-refactoring2/docs/ch12.md`）。
> 继承实用却常被误用，且往往用上一段时间遇到痛点才能察觉。本章手法：在继承体系内上下移动特性、增删类、把类型码变子类、把继承变委托。

## 12.1 函数上移 Pull Up Method（350）
反向：函数下移(359)。

**动机**：各子类中函数体相同的函数是滋生 bug 的重复，提升到超类。流程相似细节略异 → 先函数参数化(310)或塑造模板函数（Form Template Method）使之相同再提升。被提升函数引用了子类特有特性 → 先用字段上移/函数上移提升那些特性。

**做法**：
1. 检查待提升函数完全一致（不一致先重构到一致——观察差异常暴露忘记测试的行为）。
2. 检查引用的函数和字段在超类都能调到；签名不同先用改变函数声明(124)统一。
3. 超类新建函数，复制一个子类的实现。静态检查。
4. 逐个移除子类函数（一次一个，每次测试）。
5. 超类中未显式声明的依赖（如 monthlyCost），可加**陷阱函数**抛 `SubclassResponsibilityError`（向 Smalltalk 致敬），告诉子类作者必须提供实现。

## 12.2 字段上移 Pull Up Field（353）
反向：字段下移(361)。

**动机**：各子类分别开发常产生重复字段。判断字段是否重复的唯一办法：观察函数如何使用它们。上移同时去掉重复的数据声明和重复的行为。动态语言中字段在首次赋值时声明，字段上移基本是构造函数本体上移(355)的必然结果。

**做法**：检查所有使用点方式相同；名字不同先变量改名(137)统一 → 超类新建字段（protected 足够）→ 移除子类字段 → 测试。

## 12.3 构造函数本体上移 Pull Up Constructor Body（355）

**动机**：构造函数有特殊规则（调用次序限制），不能直接函数上移。太复杂时转用以工厂函数取代构造函数(334)。

**做法**：
1. 超类无构造函数则定义一个，子类调用之。
2. 移动语句(223)把子类构造函数的公共语句挪到 super() 调用之后。
3. 公共代码逐条提升到超类构造函数，引用的变量作为参数传给超类。测试。
4. 无法简单提升的公共代码（如依赖子类字段初始化之后）→ 先提炼函数(106)（如 `finishConstruction()`）再函数上移(350)。

## 12.4 函数下移 Push Down Method（359）
反向：函数上移(350)。

**动机**：超类函数只与一个/少数子类有关 → 挪到真正关心它的子类。**前提：超类明确知道哪些子类需要它**；超类不知晓时改用以多态取代条件表达式(272)。

**做法**：函数本体复制到每个需要它的子类 → 删除超类函数 → 测试 → 从不需要它的子类中删掉 → 测试。

## 12.5 字段下移 Push Down Field（361）

**动机**：字段只被一个/一小部分子类用到 → 搬到需要的子类（如"销售目标"只对 Salesman 有意义，子类比验证逻辑更能明确表达数据与类型的关系）。

**做法**：在需要它的子类中声明字段 → 从超类移除 → 测试 → 从不需要的子类删掉 → 测试。

## 12.6 以子类取代类型码 Replace Type Code with Subclasses（362）
包含旧手法：以 State/Strategy 取代类型码、提炼子类。反向：移除子类(369)。

**动机**：类型码（枚举/字符串/数字）之上的两种进阶需求：① 多个函数按类型码分支 → 引入子类后用以多态取代条件表达式(272)；② 特定字段/函数只对某类型有意义 → 子类 + 字段下移(361)。
**方案选择**：直接子类化宿主类（简单，但类型不能用在别处、类型不可变时才行）；或以对象取代基本类型(174)包装类型码再子类化（间接继承，支持类型可变，即旧 State/Strategy 手法）。

**做法**：
1. 自封装类型码字段（封装变量(132)）。
2. 任选一个类型码取值创建子类，覆写取值函数返回字面量。
3. 建选择器逻辑：直接继承方案放**工厂函数**里（用以工厂函数取代构造函数(334)；构造函数里放会与字段初始化纠缠）；间接方案可留在构造函数。
4. 测试（偏执检查：临时改子类返回值确认测试会失败，证明子类真的被用到了）。
5. 每个类型码取值重复上述过程。
6. 去掉类型码字段；验证逻辑与分发逻辑重复则删验证。
7. 用函数下移(359) + 以多态取代条件表达式(272)处理原访问类型码的函数，最后移除死代码(237)。

## 12.7 移除子类 Remove Subclass（369）
曾用名：以字段取代子类。反向：以子类取代类型码(362)。

**动机**：子类支持的变化被搬走或消失（为"未来功能"加的子类从未兑现）→ 子类存在就有阅读成本，用处太少不值得。用超类的一个字段取而代之。

**做法**：
1. 以工厂函数取代构造函数(334)封装子类创建（客户端用类型码数组决定实例化时，把判断逻辑提炼进超类的工厂函数）。
2. 有代码检查子类类型（`instanceof` 从来不是好味道）→ 提炼函数(106)包装 → 搬移函数(198)到超类（`get isMale()`）。测试。
3. 新建字段代表子类类型（可复用外部类型代码，注意给所有情况平等的默认值）。
4. 类型判断函数改用新字段；逐个把子类折叠进超类（改工厂返回超类实例 → 测试 → 删子类）。

## 12.8 提炼超类 Extract Superclass（375）

**动机**：两个类做相似的事 → 相似之处上移到新超类。合理的继承常在演化中浮现，不必预先按"真实世界分类"设计。vs 提炼类(182)：即继承 vs 委托之选；提炼超类更简单故首选，**选错有以委托取代超类(399)这瓶后悔药**。

**做法**：
1. 新建空白超类，原类继承之（需要的话先改构造函数签名）。测试。
2. 用构造函数本体上移(355)、字段上移(353)、函数上移(350)逐一上移共同元素（**先搬数据**）。
3. 子类剩余函数还有共同成分 → 提炼函数(106)再上移（名字意图一致而实现名不同 → 先改变函数声明(124)统一，如 totalMonthlyCost 与 monthlyCost）。
4. 检查客户端，考虑改用超类接口。

## 12.9 折叠继承体系 Collapse Hierarchy（380）

**动机**：继承体系演化后，类与它的超类没多大差别了 → 合并。

**做法**：
1. 选择移除超类还是子类（看哪个名字对未来更有意义；都不好就随便挑）。
2. 用字段上移/下移、函数上移/下移把所有元素移到留下的类。
3. 被移除类的引用点改指留下的类；删除空类。测试。

## 12.10 以委托取代子类 Replace Subclass with Delegate（381）

**动机**：继承的两个短板：**继承这张牌只能打一次**（多个变化方向只能选一个）；类间耦合过紧（超类修改易破坏子类，跨模块跨团队更甚）。委托都能解决，还可支持状态动态切换（`_bePremium()`）。
**何时动手**：继承工作良好时不为动而动——只在新变化方向更需要继承、或需要对象在类别间转换时。**"组合优于继承"更确切的表述是：审慎地组合使用对象组合与类继承，优于单独使用任何一种。**

**做法**：
1. 构造函数有多个调用者 → 先以工厂函数取代构造函数(334)。
2. 创建空委托类：构造函数接受**所有子类特有数据 + 指回超类的反向引用**（`this._host`）。
3. 超类加字段安放委托对象；子类创建逻辑初始化它（工厂函数中 `_bePremium(extras)`，意图更明确）。
4. 选一个子类函数用搬移函数(198)移入委托类（访问超类数据改走 `_host`）。**不删源委托代码**：
   - 函数在子类外被调用 → 把委托代码上移到超类，前面加卫语句 `this._premiumDelegate ? ... : 默认`；
   - 没有外部调用 → 移除死代码(237)。
5. 子类调用 `super` 的扩展场景（直接调 `_host.basePrice` 会无穷递归）：提炼私有基础函数 `_privateBasePrice`，或让委托提供 `extendBasePrice(base)` 由超类传入基础值再加工（后者更简洁）。
6. 子类特有函数（超类没有的）：搬入委托类，超类加分发（不存在委托时返回 undefined）。
7. 重复上述直到子类搬空；调用子类构造函数处逐个改用超类；测试；移除死代码(237)删子类。

**取代整个继承体系**（鸟的品种例）：逐个子类建委托（构造函数收 data + bird 反向引用），Bird 的选择器 `selectSpeciesDelegate` 按类型码返回委托（默认 null）。覆写默认行为的函数（如 plumage）分发麻烦 → **给各委托类提炼超类 SpeciesDelegate 承载默认行为与反向引用**，委托字段默认为该超类实例——Bird 中不再需要卫语句，继承结构转移到更收拢的范围。

代价提示：单看此重构代码复杂度上升（分发逻辑、双向引用），为的是换回"继承名额"与动态切换能力。

## 12.11 以委托取代超类 Replace Superclass with Delegate（399）
曾用名：以委托取代继承。

**动机**：合理继承的两个条件——**超类的所有函数对子类都适用**（栈不应继承列表：push/pop 之外 list 的所有操作都泄漏到栈接口上）；**子类的每个实例真的是超类的实例**（汽车不是车模——"类型与实例名不符实"的建模错误，如卷轴 extends 目录项：同一目录条目对应多份实体卷轴）。不满足即改委托：把超类变成字段，表达"这是另一个东西，我只是要用它携带的一些功能"。耦合过强时即便建模合理也可改（转发函数乏味但几乎不会出错）。

**做法**：
1. 子类（宿主类）中新建字段引用超类对象，初始化为超类实例。
2. 超类的每个函数在子类中建转发函数（设值/取值成对同时转移）。每转发一块测试。
3. 所有超类函数都有转发后，去掉继承关系。

收尾常接：多个实体应共享同一目录项 → 将值对象改为引用对象(256)：先给宿主补回自己的 id 字段（临时 null 造目录项可忍），改构造函数收 catalogID + 仓库，`catalog.get(catalogID)` 取共享引用，删多余参数。

**总态度**：先（尽量）用继承——语义条件满足时它是简洁高效的复用；发现有问题再用以委托取代超类，切换成本不高。
