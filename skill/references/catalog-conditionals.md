# 手法目录：简化条件逻辑

> 提炼自《重构（第二版）》第 10 章（`knowledgebase/book-refactoring2/docs/ch10.md`）。
> 程序的威力和复杂度都来自条件逻辑——这章是把条件逻辑变易懂的武器库。

## 10.1 分解条件表达式 Decompose Conditional（260）

**动机**：复杂条件逻辑让"发生了什么"可见、"为什么发生"不可见。把条件判断和每个分支各自提炼成函数，突出每个分支的作用**和原因**。本质是提炼函数(106)的高价值应用场景。

**做法**：对条件判断、then 分支、else 分支分别运用提炼函数(106)。完成后常用三元运算符重排：`charge = summer() ? summerCharge() : regularCharge();`

## 10.2 合并条件表达式 Consolidate Conditional Expression（263）

**动机**：一串检查各不相同、结果一致的条件 → 合并成一个表达式，表达"这其实是一次检查的多个并列条件"；也为提炼函数(106)（把"做什么"换成"为什么"）做准备。**不合并**：检查确实彼此独立、不该视为同一次检查。

**做法**：
1. 确定所有条件表达式都无副作用（有则先拆分查询函数和修改函数(306)）。
2. 顺序执行的检查用**逻辑或**合并；嵌套 if 用**逻辑与**合并。测试。
3. 重复直到全部合并。
4. 对合并结果提炼函数(106)（如 `isNotEligibleForDisability()`）。

## 10.3 以卫语句取代嵌套条件表达式 Replace Nested Conditional with Guard Clauses（266）

**动机**：条件表达式两种风格——两分支都是正常行为 → if/else；一分支正常、另一分支是罕见异常 → **卫语句**（条件为真时做必要整理立即返回）。卫语句告诉读者："这不是核心逻辑关心的，发生了就处理完退出"。不必拘泥"单一出口"教条，清晰才是关键。

**做法**：
1. 选最外层需替换的条件逻辑，换成卫语句（常常需要**反转条件**：`capital > 0` 的嵌套 → `capital <= 0) return`）。测试。
2. 重复。
3. 所有卫语句引发同样结果时用合并条件表达式(263)合并。
4. 顺手删掉因此多余的 result 可变变量。

## 10.4 以多态取代条件表达式 Replace Conditional with Polymorphism（272）

**动机**：两种适用场景：
1. **类型码体系**：多个函数都有基于同一类型码的 switch（图书/音乐/食品各自处理）→ 每种类型一个类，多态承载各自行为。**越多函数依赖同一套类型码分支，多态越有益**。
2. **基础逻辑 + 变体**：基础逻辑放超类先理解之，变体各自放子类、只强调与基础的差异（如 ExperiencedChinaRating）。
**不滥用**：大部分条件逻辑用 if/else 和 switch 就够了，不必劳师动众引入多态。

**做法**：
1. 尚无多态结构时：先函数组合成类(144)建类；再用**工厂函数**（switch 按类型返回子类实例；JS 构造函数不能返回子类）替换构造调用。
2. 把带条件逻辑的函数移到超类（未提炼的先提炼函数(106)）。
3. 任选一个子类建函数覆写超类的条件函数，复制对应分支进去并调整；超类对应分支先临时抛异常（偏执检查）。测试。
4. 重复处理其他分支。
5. 超类函数保留默认逻辑；或声明 abstract/直接抛 `subclass responsibility`。

变体场景技巧：不能整段搬的差异逻辑，先提炼出小函数（哪怕名字带 And 不好看）供子类覆写，之后再改名、拆分整理；子类常用 `super.x - 2` 表达"在基础上的差异"。

## 10.5 引入特例 Introduce Special Case（289）
曾用名：引入 Null 对象。

**动机**：多处客户端以**同样方式**应对同一个特殊值（"unknown"、null）→ 特例对象收拢共用行为，消掉大量重复检查。Null 对象是特例的特例。表现形态：只读数据用字面量对象；要更多行为用类；可经封装类返回或经变换插入。

**做法**：
1. 给重构目标添加"检查特例"属性（正常类返回 false）。
2. 创建特例对象/字面量，该属性返回 true（动态类型语言不必继承）。
3. **关键技巧**：先对"与特例值比对"的代码提炼函数(106)成 `isUnknown(arg)`（内放陷阱抛错捕捉意外值），所有客户端逐个改用它（每次测试）——避免"改数据源和改检查"被迫一大步完成。
4. 数据源改为返回特例对象；isUnknown 函数体改用属性判断。全文搜索确认无残留字符串比较。测试。
5. 把各客户端的通用特例处理搬进特例对象（name 返回 "occupant"；billingPlan 返回 basic、设值函数做空操作——**特例对象是不可变值对象**；关联对象也返回特例：`paymentHistory` → NullPaymentHistory）。
6. 客户端条件代码消失；个别需要不同处理的客户端保留 `aCustomer.isUnknown` 检查；无人使用的全局 isUnknown 用移除死代码(237)删除。

记录场景：加一个变换函数（深复制 → 填充 isUnknown → 逐步放入特例字面量），检查函数兼容新旧两种形态。

## 10.6 引入断言 Introduce Assertion（302）

**动机**：代码"只有某条件为真才能正常运行"的假设通常隐藏着，断言把它显式表达。断言**应该是交流形式**——告诉读者程序在此处对状态做了什么假设；即便 bug 修了也倾向保留。断言失败不应被捕捉、可完全禁用而不改变行为。

**做法**：发现假设就加断言（永远行为保持）。放设在**污染源头上**更好（设值函数断言，而不是使用处断言——否则失败后还得追溯坏值的来路）。

**纪律**：
- 只断言"**必须为真**"的条件，不检查"我认为应该为真"的（滥用造成重复，可先用提炼函数(106)去重）。
- 只用于防程序员的错误；外部输入的校验是一等公民逻辑，不用断言（对外部数据源有绝对信心除外）。
- 讽刺但真：只有确信断言绝不会失败时才用它。
