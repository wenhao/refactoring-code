# 手法目录：重构 API

> 提炼自《重构（第二版）》第 11 章。括号内数字为原书页码，仅供人工溯源。
> 模块和函数是软件的骨肉，API 是连接它们的关节。

## 11.1 将查询函数和修改函数分离 Separate Query from Modifier（306）

**动机**：无副作用的查询函数可任意调用、任意搬移、易测试。好规则：**命令与查询分离（CQS）——任何有返回值的函数都不该有看得到的副作用**（缓存等"察觉不到的"状态改变不算）。既返回又修改的函数要拆开。

**做法**：
1. 复制整个函数，按查询功能命名（想不出名字就看返回值被填入的变量叫什么）。
2. 从新查询函数中去掉所有副作用语句。静态检查。
3. 用到返回值的调用处改为"调查询函数 + 紧接着调原函数"，每次测试。
4. 原函数去掉返回值。测试。
5. 清理两个函数间的重复（常用替换算法(195)让修改函数复用查询函数）。

## 11.2 函数参数化 Parameterize Function（310）
曾用名：令函数携带参数。

**动机**：两个函数逻辑非常相似、只有字面量值不同 → 合并为一个带参数的函数，消除重复且能处理更多值。

**做法**：
1. 从相似函数组中选一个（多个范围/档次时**从中间的入手**较好）。
2. 改变函数声明(124)添加参数（顺手改名表意），调用处传字面量。测试。
3. 函数体内字面量**逐个**换成参数，每换一个测试。
4. 其他相似函数的调用处逐个改为调参数化函数（不能直接替换就先调整），每次测试。

范围类参数化常用 `Infinity` 作开区间上界；失去必要性的卫语句可留作文档（阐明负输入的处理）。

## 11.3 移除标记参数 Remove Flag Argument（314）
曾用名：以明确函数取代参数。

**动机**：标记参数 = 调用者传字面量指示函数执行哪部分逻辑（布尔尤糟：`bookConcert(c, true)` 看不出 true 是什么）。它隐藏了函数调用的差异性。**判别**：传入程序中流动的数据不算标记参数；只有字面量直传、且参数值影响函数内部控制流，才是。

**做法**：
1. 为参数每种可能值新建一个明确函数（`rushDeliveryDate` / `regularDeliveryDate`）：
   - 主函数有清晰的外层条件分发 → 分解条件表达式(260)拆出；
   - 分发逻辑纠缠在内部难剥到顶层 → 在原函数之上建**包装函数**（强行转调 `deliveryDate(order, true)`）。
2. 字面量调用者逐个改为明确函数。
3. 全部迁完删除原函数（或限制可见性/改名为 `xxHelperOnly`）；有传正常数据的调用者则保留原函数形成双接口。

多个标记参数 → 可能该函数做太多了，考虑拆分组合。

## 11.4 保持对象完整 Preserve Whole Object（319）

**动机**：从记录抽出几个值又一起传给函数 → 直接传整个记录：应对"需要更多数据"的变化不用改参数列表，调用更短；还能把处理这组数据的逻辑搬进完整对象（常见于引入参数对象(140)之后；抽取值单独操作是依恋情结信号）。**不做**：不想让被调函数依赖完整对象（尤其跨模块）时。特例：调用者可把 `this` 作为参数传自己。

**做法**：
1. 新建空函数用期望的参数列表（完整对象），起**易搜索的临时名**（如 `xxNEWwithinRange`）。
2. 函数体内调旧函数，把新参数映射到旧参数列表。静态检查。
3. 调用处逐个换用新函数，每次测试；导出参数值的代码用移除死代码(237)清理。
4. 全部替换后内联函数(115)把旧函数并入新函数。
5. 去掉临时前缀改名回旧名。

另一条完全由手法组合成的路径：提炼变量(119)（调用、参数各一个变量）→ 提炼函数(106) → 搬移函数(198)到目标类 → 内联变量。工具支持可靠时更流畅。

## 11.5 以查询取代参数 Replace Parameter with Query（324）
曾用名：以函数取代参数。反向：以参数取代查询(327)。

**动机**：参数列表应总结函数的可变性且避免重复。调用者传入的值若函数自己同样容易获得，就是重复——去掉参数把"获得正确值"的责任移交给函数（习惯上简化调用方）。
**最安全场景**：一个参数可由另一个参数推导出来。**不做**：给函数体增加不必要的依赖（访问不想让它知道的元素/想剥离的数据）；不想让具**引用透明性**的函数失去该品质（不让它去读可变全局）。

**做法**：
1. 必要时提炼函数(106)把参数的计算过程独立成函数。
2. 函数体内对该参数的引用逐个改为调用新函数，每次测试。
3. 改变函数声明(124)删掉该参数。

## 11.6 以参数取代查询 Replace Query with Parameter（327）
反向：以查询取代参数(324)。

**动机**：函数体内有令人不快的引用（全局变量、想移除的元素）→ 改为参数，把处理引用的责任交还调用者。**引用透明性**：把不具引用透明性的元素变成参数，函数重获"同参数同结果"，更易测试理解（常见模式：核心模块全是纯函数，I/O 包在外围）。**代价**：调用者变复杂——责任分配的决策不容易也不一劳永逸，所以要熟练这对双向手法。

**做法**：
1. 对查询代码用提炼变量(119)从函数体分离。
2. 对剩余函数体用提炼函数(106)（易搜索临时名）。
3. 内联变量(123)消除刚提炼的变量，旧函数只剩一行调用。
4. 内联函数(115)展开到调用方。
5. 新函数改名回原名。

调用方变笨重是常态——这是降低耦合的代价。

## 11.7 移除设值函数 Remove Setting Method（331）

**动机**：提供设值函数就暗示字段可变。不希望创建后再变的字段就不给设值函数（同时声明不可变），意图清晰且排除误用。两种情况：构造函数是设值函数唯一使用者；客户端用"创建脚本"（构造 + 一串设值）构造对象，脚本执行完字段不应再变。

**做法**：
1. 构造函数拿不到值则用改变函数声明(124)加入参数，构造函数内调用设值函数（多个设值函数可一次性全传入）。
2. 构造之外的设值调用逐个改为新构造函数，每次测试。**不能替换为"创建新对象"（如共享引用的对象）时放弃本重构**。
3. 内联函数(115)消去设值函数，字段声明为不可变。测试。

## 11.8 以工厂函数取代构造函数 Replace Constructor with Factory Function（334）

**动机**：构造函数的局限：只能返回本类实例（不能按环境/参数返回子类或代理）、名字固定（不能比类名更清晰）、需要 new 等特殊调用方式。工厂函数不受限。

**做法**：
1. 新建工厂函数调用现有构造函数。
2. 构造调用逐个改为工厂函数，每次测试。
3. 尽量缩小构造函数的可见范围。

加分项：针对类型码字面量（`createEmployee(name, "E")` 是坏味道）建语义化工厂（`createEngineer(name)`），把类型信息编进函数名。

## 11.9 以命令取代函数 Replace Function with Command（337）
曾用名：以函数对象取代函数。反向：以函数取代命令(344)。

**动机**：命令对象（封装一次函数调用请求的对象）提供更大灵活性：撤销、生命周期管理、继承/钩子定制、拆解复杂函数（方法和字段替代嵌套函数，各方法可单独测试调试）。**但灵活性以复杂性为代价——95% 的时候选普通函数**，只有特别需要命令独有的能力时才用。

**做法**：
1. 为函数创建空类（按函数命名）。
2. 搬移函数(198)把函数移入类，原函数保留为转发函数。
3. 执行函数按语言规范命名（execute/call）。
4. 逐个把参数变成构造函数参数 + 字段（`new Scorer(candidate, ...).execute()`）。

拆解套路（做这个重构的常见目的）：把**所有局部变量逐个提升为字段** → 状态全在对象上 → 放心用提炼函数(106)拆碎 execute，不再受局部变量作用域牵制。

## 11.10 以函数取代命令 Replace Command with Function（344）
反向：以命令取代函数(337)。

**动机**：命令对象不够复杂时费而不惠——只想调用一个函数让它干活，就变回普通函数。

**做法**：
1. 提炼函数(106)把"创建并执行命令"包成一个函数（它将取代命令对象）。
2. 对命令对象执行阶段用到的支持函数逐个内联(115)（有返回值的先提炼变量(119)再内联）。
3. 改变函数声明(124)把构造函数参数转移到执行函数；字段引用逐个改为参数（每次测试；顺手删掉构造函数中的字段赋值，漏改会有测试兜底）。
4. 把"构造 + 执行"全部内联到调用方。测试。
5. 移除死代码(237)删除命令类。
