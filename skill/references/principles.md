# 重构的原则与心态

> 提炼自《重构（第二版）》第 1、2、5 章。已覆盖：ch1、ch2。

## 何谓重构（严格定义）

- **重构（名词）**：对软件内部结构的一种调整，目的是在不改变软件可观察行为的前提下，提高其可理解性，降低其修改成本。
- **重构（动词）**：使用一系列重构手法，在不改变软件可观察行为的前提下，调整其结构。
- 与"结构调整"的区别：重构运用大量微小且保持行为的步骤，**过程中代码几乎从不进入不可工作状态**，任何时刻都可以停下来。
- 与性能优化的区别：两者都不改变整体功能，但重构求"易理解、易修改"（可能更快也可能更慢），优化求"更快"（可能更难维护）。
- 重构期间发现 bug：重构完成后 bug 应仍存在（也可当即顺手修掉，但要明确这是换帽子）。

## 重构的节奏感（ch1 的核心教训）

**小步修改，每步之后代码都处于可工作状态。** 每次微小改动后：编译 → 测试 → 提交。
测试失败且无法立即定位时：回滚到最后一个绿色提交，用更小的步子重做——而不是边修边继续。

"小的步子可以更快前进" —— 步子越小，犯错时排查范围越小，反而总体速度更快。

## 两顶帽子（Kent Beck）

- **加功能帽**：不修改既有代码，只添加；用测试通过衡量进度。
- **重构帽**：不加任何功能、不添加测试（只允许为应对接口变化修改测试）。
- 可以频繁换帽子（几分钟一换），但**任何时刻都清楚自己戴着哪顶**。重构与加功能尽量分开提交（除非交织太紧）。

## 为何重构（经济驱动，不是道德洁癖）

1. **改进软件的设计**：设计会腐坏，重构维持形态。核心方向是消除重复——"所有事物和行为只表述一次"是优秀设计的根本。
2. **使软件更容易理解**：源码的读者不只是计算机，还有未来的修改者（常是未来的自己）。
3. **帮助找到 bug**：重构加深理解，把理解写回代码的同时验证了假设。
4. **提高编程速度**（设计耐久性假说）：内部质量良好 → 修改点好找、只需理解一小部分、bug 少 → 开发长期保持快速。代码库逐步演化成构建新功能的平台。

## 何时重构

- **三次法则**：第一次直接做，第二次容忍反感再做，第三次重构。事不过三，三则重构。
- **预备性重构**（加功能前/修 bug 前）：先让修改变容易，再做容易的修改。"往东 100 公里，先往北上高速。"
- **帮助理解的重构**：凡自问"这段代码在做什么"，就是机会；初步重构像扫去窗上尘埃，让后续看不见的设计问题显形。
- **捡垃圾式重构**：路过发现垃圾，容易修就马上修；费劲就记下来稍后回来。营地法则：至少让营地比到达时更干净。
- **见机行事 > 有计划**：重构是编程的自然部分，不专项安排时间（正如不专项安排写 if）。漂亮的代码也需要重构——昨天的合理权衡今天就可能不再合理。
- **长期重构**：大改造（换库、抽组件）不设专门团队，全团队共识渐进推进；用**Branch By Abstraction**：先引入兼容新旧接口的抽象层，调用方全部迁移后再替换底层。
- **代码复审时重构**：复审中提出的建议立即重构验证，"不必想象代码什么样，可以直接看见"。

## 何时不重构

- 凌乱但**不需要修改**的代码（丑代码藏在稳定的 API 之下）。
- **重写比重构更容易**时（需判断力；不花时间试一试往往难以真实评估）。
- 很少触碰、不常带来麻烦的代码，倾向于不动。
- 没想清楚优化方向时可以推迟（或先做实验）。

## 重构的挑战与应对

- **"拖慢进度"的质疑**：重构的唯一目的是开发更快。绝大多数团队重构不足而非过度。
- **代码所有权**：已发布接口（published interface）不能改调用方 → 保留旧声明作为委托函数，标记 deprecated，择期退役。推荐团队所有制而非细粒度强所有制。
- **分支**：特性分支越长，语义冲突指数上升，重构（大量小改名/小移动）尤其易冲突 → 尽量持续集成/主干开发，或至少每天集成。
- **测试**：自测试代码是重构第一基石。无测试时：只用可信赖的自动化（语法树级）重构工具，或采用经验证的"安全重构手法集"。
- **遗留代码**：先找**接缝**插入测试（参《修改代码的艺术》），把系统置于测试覆盖下；随时重构触碰到的部分，不搞一次性大翻新。
- **数据库**：结构变更与数据迁移脚本一起版本化，小步迁移保持每次可运行；跨发布用**并行修改（expand-contract）**：加新字段 → 双写 → 逐个切读 → 观察 → 删旧字段。

## 重构、架构与 YAGNI

- 不再"先设计后编码"：需求难以预先充分理解，重构使架构可以持续演进。
- **YAGNI（你不会需要它）**：只按当前需求构造软件、保证设计质量；不为猜测的未来加灵活性机制（参数、钩子）。
- 判断标准：评估"**以后再重构有多困难**"——只有当未来重构会很困难时，才现在加灵活性。
- 不会增加复杂度的灵活性（命名良好的小函数）可以随手引入。

## 重构与性能

三种编写快速软件的方法：
1. **时间预算法**：仅用于硬实时系统。
2. **持续关注法**：处处小心性能——通常劳而无获，且损害可维护性。
3. **度量优化法（推荐）**：先写出构造良好的程序，进入优化阶段后用性能分析工具找**热点**（程序大半时间耗在一小半代码上，一视同仁地优化 90% 是白费），集中优化热点；小步调优，每步度量，无改善就撤销。

**先度量，不要臆测**（Ron Jeffries 的教训：凭全盘了解推测性能热点，结果全错）。
重构可能短期变慢，但使调优更容易：好代码粒度细、理解清，调优反而快。

## 好代码的检验标准

**人们是否能轻而易举地修改它。** 不是行数少、不是"优雅"，而是：修改点容易找到、改得快、不易引入错误。
为明确性增加包装（代码行数变多）是值得的——可演化的软件以明确为贵。

## 从 ch1 示例提炼的典型手法链（长函数分解）

分解一个长函数的经典顺序：

1. **先建立测试**（返回值/输出对比的自检验测试）。
2. 找出函数内一段有独立意图的代码，**提炼函数**；命名 = 你的理解。
3. 提炼后立即审视：**改名**（返回值统一叫 `result`；动态类型语言参数带类型名如 `aPerformance`）。
4. **移除临时变量**是后续提炼的前提：
   - 只读临时变量 → 以查询取代临时变量（提炼成函数再内联）
   - 累加变量 → 拆分循环 → 移动语句集中 → 提炼函数 → 内联变量（四步）
5. 需要复用计算逻辑时 → **拆分阶段**：阶段一计算并填充中转数据结构，阶段二只做渲染；两阶段可分文件。
6. 类型码 switch 分散多处 → 先建类把计算搬进去 → **以工厂函数取代构造函数**按类型返回子类 → **以多态取代条件表达式**（分支逐个下移到子类，超类默认实现或抛 `subclass responsibility`）。
   - 判断继承方案是否值得：**越多函数依赖同一套类型码做分支，多态越有益**。

## 风格细节（来自作者示范）

- 不修改传入的参数数据，尽量保持不可变（如 `Object.assign({}, src)` 复制后加工）。
- 删除"多余且会引起误解"的注释——好的提炼与命名让注释失业。
- 遇到命名冲突（函数名被变量占用），先随便起个名，内联变量后再改回好名字。
- 中转数据结构让多态设计（计算器）对使用者不可见。
