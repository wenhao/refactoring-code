# 手法目录：封装

> 提炼自《重构（第二版）》第 7 章（`knowledgebase/book-refactoring2/docs/ch7.md`）。
> 主题：隐藏模块的秘密——数据结构、基本类型、临时变量、类的内部、类间关系、算法。

## 7.1 封装记录 Encapsulate Record（162）
曾用名：以数据类取代记录。

**动机**：可变数据偏爱类对象胜过记录：对象能隐藏"存储的字段"与"计算出的字段"的区别，且支持渐进式字段改名（新旧访问函数并存）。**不可变数据则可直接用记录**（改名=复制新字段逐步替换引用）。散列/字典类记录在使用范围变宽后"持有什么字段"不再直观，值得封装；嵌套的待序列化结构（JSON/XML）同理。

**做法**：
1. 封装变量(132)包住记录变量（函数起一个**容易搜索的丑名字**，故意不打算让它长命）。
2. 创建类包装记录，变量值换成类实例；类上先提供返回原始记录的访问函数。
3. 测试。
4. 新建返回类对象的函数；逐个使用点改为类对象 + 字段访问函数（不存在则创建），每次测试。**更新点最优先处理**——凸显并集中更新操作是封装的核心。
5. 删除返回原始记录的函数。测试。
6. 复杂/嵌套结构：读取可返回深复制副本或只读代理；字段本身复杂则递归再封装。
7. 验证替换是否彻底：让 raw 访问返回深复制，遗漏的更新点会因测试失败暴露。

## 7.2 封装集合 Encapsulate Collection（170）

**动机**：常见错误是只封装集合变量的引用，取值函数仍返回原始集合——客户端可直接增删成员而类全然不知。应提供 add/remove 方法让修改必经类。取值返回**只读代理或副本**。反对"永不返回集合、全用类方法（numberOfOrders）"的做法——丧失集合管道等组合能力。同一代码库内**只用一种方案保持一致**。

**做法**：
1. 集合引用未封装则先封装变量(132)。
2. 类上添加 add/remove 元素函数（remove 可带"不存在时"的处理回调，默认抛错）。
3. 有设值函数则尽量用移除设值函数(331)去掉；不能去则设值时复制一份存入。
4. 静态检查；把直接修改集合的调用点改为 add/remove，每次测试。
5. 取值函数改为返回副本（`this._courses.slice()`）或只读代理。测试。

习惯：凡"看起来可能改变集合"的操作都返回副本（注意 JS 的 `sort()` 会改原数组）。

## 7.3 以对象取代基本类型 Replace Primitive with Object（174）
曾用名：以对象取代数据值/以类取代类型码。

**动机**：开发初期用字符串/数字表示"电话号码""优先级"这类概念，随后格式化、区号、比较等逻辑扩散各处造成重复。**一旦对某个数据的操作不止于打印，就为它建类**。小值对象起初价值甚微，但会成长为工具（校验、比较逻辑有地可放）。老手最常用重构之一，常被新手低估。

**做法**：
1. 未封装先封装变量(132)（自封装字段，暂放任引用点）。
2. 为数据值创建简单类：构造函数存值 + `toString()` 转换函数（比取值函数更能传达"数据转换"）。
3. 静态检查。
4. 设值函数改为创建新类对象存入字段；取值函数改为 `.toString()`。测试。
5. 函数改名(124)反映真实用途（如 `priorityString`）。
6. 需要时提供返回对象本身的取值函数；构造函数宽容接收同类型实例（`if (value instanceof Priority) return value`）。
7. 向类里加行为：合法性校验、`equals`/`higherThan`/`lowerThan` 等比较逻辑——成为值对象。

## 7.4 以查询取代临时变量 Replace Temp with Query（178）

**动机**：把只读临时变量升级为函数：分解长函数时无须传参、设立清晰边界暴露依赖与副作用、多处可复用计算。在类中效果最好（共同上下文）。
**适用限定**：只适用于"计算一次、之后不再修改"的变量；多次赋值可把所有计算一并提炼进查询（须每次结果一致）；**快照型变量**（如 oldAddress）不适用。

**做法**：
1. 确认变量使用前已计算完毕、计算结果恒定。
2. 可只读化的先改为只读。测试。
3. 赋值代码段提炼成函数（名字冲突则先起临时名）。**若有副作用先用拆分查询函数和修改函数(306)隔离**。测试。
4. 内联变量(123)移除临时变量。

## 7.5 提炼类 Extract Class（182）
反向：内联类(186)。

**动机**：类随责任累积变成乱麻。信号：某些数据和函数总是一起出现/同时变化；搬走它们后其他部分变得无意义；子类化只影响类的部分特性，或不同特性需要不同的子类化方式。

**做法**：
1. 决定如何分解责任。
2. 创建新类表现分离出的责任；旧类剩余责任与名称不符则先改名。
3. 构造旧类时创建新类实例，建立连接。
4. 逐个字段用搬移字段(207)搬移，每次测试。
5. 用搬移函数(198)搬移函数——**先搬底层函数**（被调用多于调用别人者），每次测试。
6. 检查两端接口，删掉不再需要的函数，按新环境改名（如 telephoneNumber → toString）。
7. 决定是否公开新类；公开则考虑将引用对象改为值对象(252)。

## 7.6 内联类 Inline Class（186）
反向：提炼类(182)。

**动机**：类不再承担足够责任（被之前的重构搬空了）；或想重新安排两个类的职责——先内联合并再按更好的边界重新提炼，常比直接搬移更简单。

**做法**：
1. 对源类每个 public 函数，在目标类建委托函数。
2. 源类方法的引用点逐个改为调用目标类委托函数，每次测试。
3. 把源类的函数与数据全部搬进目标类（可用内联函数(115)、简化版搬移字段），每次测试，直到源类成空壳。
4. 删除源类。

## 7.7 隐藏委托关系 Hide Delegate（189）
反向：移除中间人(192)。

**动机**：客户端经服务对象的字段取受托对象再调用（`aPerson.department.manager`），就必须知晓委托关系；受托类接口一变波及所有客户端。在服务对象上放一个简单委托函数（`aPerson.manager`），变化只影响服务对象。

**做法**：
1. 为每个受托类函数在服务对象上建委托函数。
2. 客户端逐个改为只调服务对象，每次测试。
3. 若再无客户端需要取受托对象本身，移除服务对象上的相关访问函数。测试。

## 7.8 移除中间人 Remove Middle Man（192）
反向：隐藏委托关系(189)。

**动机**：受托类特性越来越多，服务类的转发函数堆积成"中间人"味道（常见于狂热遵循迪米特法则时）。隐藏的合适程度会随时间变化——**有了这对双向手法就不必纠结：随时调整，"重构者永远不必说对不起"**。

**做法**：
1. 为受托对象创建取值函数。
2. 每个委托函数的客户端逐个改为链式调用（`aPerson.department.manager`），每次测试。
3. 删掉委托函数。（工具变招：先封装变量(132)再内联函数(115)。）

可以混用：常用的委托关系保留（客户端友好），其余移除。

## 7.9 替换算法 Substitute Algorithm（195）

**动机**：发现做同一件事有更清晰的方式（更简单算法、程序库已提供同等功能、想先换成易修改的算法再改行为）。

**做法**：
1. 先尽量把原算法**分解为简单小函数**——替换巨大复杂的算法非常困难。
2. 确保算法已被抽到独立函数中，用测试**固定其行为**。
3. 准备替换算法。静态检查。
4. 跑测试比对新旧结果；通过即完成，失败则以旧算法为参照标准调试。
