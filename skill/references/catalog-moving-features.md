# 手法目录：搬移特性

> 提炼自《重构（第二版）》第 8 章。括号内数字为原书页码，仅供人工溯源。
> 主题：在上下文之间搬移函数、字段、语句；处理循环；删除死代码。

## 8.1 搬移函数 Move Function（198）
曾用名：搬移方法。

**动机**：模块化的本质是"互相关联的要素集中一块、块间联系直观"。最直接动因：函数频繁引用其他上下文的元素、对自身上下文关心甚少（依恋情结）。帮手函数可能有更通用的去处。**决定越难做，重要性通常越低——先安置过去看是否契合，不合适再搬**。搬移一组函数前可能需要先用函数组合成类(144)/提炼类(182)建新上下文。

**做法**：
1. 检查函数引用的所有元素，考虑是否一并搬移；被调用的函数也要搬则**先搬它们**（从依赖最少的入手）。子函数仅被它调用时可先内联，搬完再重新提炼。
2. 检查多态性（是否覆写/被覆写）。
3. 复制函数到目标上下文并适应新家（改名让作用域差异一目了然，暂用临时名；用到源上下文元素则以参数或上下文引用传入）。静态检查会揪出未定义符号——顺藤摸瓜把该搬的（如内部 distance/radians 链）也搬过来。
4. 静态检查。
5. 源函数改为纯委托函数。测试。
6. 考虑内联源函数去掉中间人；调用方直接调用不费周折就删。
7. 给目标函数起正式名字（顶层函数可见性最高，值得好名字；与变量撞名就先内联变量）。

类间搬移：先观察用到的每个特性该跟谁走；留不住的数据可先传值、需要更多再改传整个对象。警惕嵌套函数里藏私有共享数据——优先提升到模块顶层用模块机制控制可见性。

## 8.2 搬移字段 Move Field（207）

**动机**：**数据结构是健壮程序的根基**，坏结构招致纠缠代码。搬移信号：一条记录的字段总是与另一条记录一起作为参数传递；修改一条记录总需同时改另一条；更新一个字段要在多处结构中同步。发现数据结构不适应需求就马上修——瑕疵会累积。

**做法**：
1. 确保源字段已良好封装。测试。
2. 目标对象上创建字段（及访问函数）。静态检查。
3. 确保源对象能引用到目标对象（现成字段/方法，或新建，可临时）。
4. 调整源对象的访问函数改用目标字段。测试。
   - 共享对象场景（多实例共享目标）：先让设值函数双写两边 → 引入断言(302)检测不一致 → 观察一段时间确信无行为变化 → 访问函数直接用目标字段。
   - 裸记录无封装：先封装记录(162)再搬。
5. 移除源字段。测试。

注意：把字段搬去共享对象（如利率搬到账户类型）**只有在同类实例值确实相同时才是重构**，否则改变可观察行为——用断言/日志验证。

## 8.3 搬移语句到函数 Move Statements into Function（213）
反向：搬移语句到调用者(217)。

**动机**：消除重复——调用某函数时总有相同代码每次都要执行，合并进函数，改一处全体生效。日后需要差异时再用反向手法搬出。

**做法**：
1. 重复代码段离调用点远则先移动语句(223)挪到紧邻。
2. **只有一个调用点**：直接剪切粘贴进函数，测试，完成。
3. **多个调用点**：选一个调用点，把"待搬语句 + 目标函数调用"一起提炼函数(106)（临时名易搜索）→ 其余调用点逐个改调新函数（每次测试）→ 内联函数(115)把原目标函数并入新函数并删除 → 新函数改名(124)回原名（或更好的名字）。

## 8.4 搬移语句到调用者 Move Statements to Callers（217）
反向：搬移语句到函数(213)。

**动机**：抽象边界随系统演进漂移——曾是整体的函数行为，如今某些调用点需要不同表现。把差异行为搬到调用处。**边界偏移太远时不适用**：改用内联函数(115)合并双方、调整顺序、重新提炼出合适边界。

**做法**：
1. 简单情况（原函数简单、调用者一两个）：直接剪切粘贴回调用端，测试即完成。
2. 调用点多：先用提炼函数(106)把**想留下的代码**提炼成临时名新函数（原函数变临时函数 + 待搬语句）；超类方法有子类覆写时每个子类做同样提炼再删，统一引用超类的。
3. 对原函数逐个调用点用内联函数(115)（留下：临时函数调用 + 搬出的语句）。
4. 删除空壳原函数，临时函数改名(124)回原函数名。

## 8.5 以函数调用取代内联代码 Replace Inline Code with Function Call（222）

**动机**：内联代码做的事已有现成函数（尤其库函数），用调用消除重复。**例外**：只是外表相似并无本质联系时不该替换——判据是函数名放进内联代码语境是否协调（不协调=命名糟糕或用途确实不同）。

**做法**：内联代码替换为函数调用，测试。

## 8.6 移动语句 Slide Statements（223）
曾用名：合并重复的条件片段。

**动机**：让相关的东西在一起（同一数据结构的取用、变量声明与使用）。常是提炼函数(106)前的准备工作——不先聚拢就没法提炼。声明习惯：在第一次使用处声明，而非函数顶部。

**做法**：
1. 确定目标位置；检查途经语句是否会被干扰，会则放弃。
2. 安全性规则（参考而非绝对）：
   - 前移：不能移过片段中所声明变量的任何引用/赋值；
   - 后移：不能移到"引用了片段中变量"的语句之后；不能移到"修改了片段所引用变量"的语句之后；片段修改某元素时不能移过引用该元素的语句。
3. 剪切粘贴。测试。
4. 测试失败→减小步子（少移几行/少移几次）；或提示时机未到，先做别的重构。

无副作用的代码几乎可随心重排——这是尽量写无副作用代码（命令-查询分离）的价值。移动前可先拆分变量(240)消除状态更新。条件分支中的相同语句可移出 if-else 消除重复（反向亦可）。

## 8.7 拆分循环 Split Loop（227）

**动机**：身兼多职的循环让每次修改都要同时理解几件事；拆成一个循环一件事，修改只需理解相关循环，且更易提炼成函数（单值返回）。担心两遍循环的性能？先重构再优化；循环很少成为瓶颈，拆开反而使更强优化成为可能。

**做法**：
1. 复制一遍循环。
2. 删除每个循环中的重复计算，使各只做一件事（无副作用的代码可暂留）。测试。
3. 对每个循环应用提炼函数(106)（先移动语句把相关变量聚拢）；常可进一步以管道取代循环(231)/替换算法(195)。

## 8.8 以管道取代循环 Replace Loop with Pipeline（231）

**动机**：集合管道（map/filter 等运算链）一次从头读到尾就能看清集合的变换过程，可读性强于循环。

**做法**：
1. 创建新集合变量存放参与循环的集合（可复制现有变量）。
2. 从循环顶部开始，逐块行为搬出、用管道运算替代（slice 掉表头、filter 空行、map 拆分、filter 条件、map 成目标形状……），每次修改测试。顺带消灭控制变量（firstLine 之类）。
3. 全部搬完删除循环；有累加变量则把管道结果赋给它（通常再内联变量）。

## 8.9 移除死代码 Remove Dead Code（237）

**动机**：无用代码是纯思维负担——没有任何标记告诉读者可以放心忽略；版本控制系统已经普及，"注释掉留着"是过时做法。需要时随时能从历史找回。

**做法**：
1. 死代码可从外部引用（如独立函数）时先查有无调用点。
2. 删除。测试。
