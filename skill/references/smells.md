# 代码的坏味道（Bad Smells）→ 重构手法映射

> 提炼自《重构（第二版）》第 3 章。诊断时通读此表，对照目标代码找出最疼的一个味道——一次只攻击一个。
> 手法后括号中的数字为原书页码，仅供人工溯源。

判断原则：没有任何量化标准比得上见识广博者的直觉。坏味道是"这里有一个可以用重构解决的问题"的迹象，不是必须立刻整改的判决。

## 重要展开

### 过长函数（最常遇到的坏味道）
- 关键不在长度，在"**做什么**"与"**如何做**"之间的语义距离。
- 99% 的场合用提炼函数(106)即可。
- **寻找注释**：注释指出语义距离，是提炼的信号；哪怕一行代码只要需要注释就值得提炼，函数以用途（而非实现手法）命名。
- 参数/临时变量阻碍提炼时：以查询取代临时变量(178)、引入参数对象(140)、保持对象完整(319)；杀手锏：以命令取代函数(337)。
- switch 每个分支提炼成函数(106)；多个 switch 基于同一条件 → 以多态取代条件表达式(272)。
- 循环连同循环体提炼；提炼出的循环难命名 → 说明做了几件事 → 拆分循环(227)。

### 神秘命名
命名是编程最难的两件事之一。**想不出好名字，说明背后潜藏更深的设计问题**——纠结命名常能推动代码精简。

### 重复的 switch vs 单个 switch
反对的是"重复"，不是 switch 本身：同样的 switch/else-if 逻辑散布多处，每加分支都要找齐所有副本更新——这时才上多态。

### 可变数据
作用域越大风险越大。派生出的可变数据（能在别处算出来）尤其刺鼻 → 以查询取代派生变量(248)。

### 发散式变化 vs 霰弹式修改（方向相反）
- 发散式变化：**一个模块**因**不同原因**变化 → 拆开模块（拆分阶段/搬移/提炼类）。
- 霰弹式修改：**一种变化**要改**很多模块** → 聚拢（搬移到一处；不确定聚到哪就先内联成一大块再重新拆）。

### 依恋情结的归属判断
函数用了几个模块的功能时：**看它用谁的数据最多就搬去谁家**。先分解成小函数再分别安置会更容易。策略/访问者模式是刻意例外（为对抗发散式变化付出间接性代价）。

### 数据泥团的检验
删掉其中一项数据，其余的若失去意义 → 该为它们建一个类。建类后顺势找"依恋情结"，把行为搬进来。

### 纯数据类的合法例外
拆分阶段(154)产生的**不可变**中转数据结构无须封装行为——不可变字段可直接读取，不必强加取值函数。

### 注释的正确用法
需要解释"做了什么"→ 提炼函数；提炼后仍需解释 → 改名；需要说明需求规格 → 引入断言(302)。
**注释的良好时机**：记录"为什么这么做"、标记没把握的区域、记述将来的打算。
