# 重构既有代码（Refactoring）

## 核心理念

重构是在**不改变代码可观察行为**的前提下，调整代码结构，使其**更易理解、更易修改**。
两条铁律：

1. **小步前进**：每次只做一个微小改动（通常 3~8 分钟），改完立即验证；任何时刻代码都处于可工作状态，随时可以停。
2. **依赖于测试**：看到红条绝不重构；测试失败且无法立即定位时，回滚到上一个绿色提交，换更小的步子重做。

好代码的检验标准只有一个：**人们是否能轻而易举地修改它**。

> 本技能提炼自《重构：改善既有代码的设计（第二版）》（中文版）全书 12 章，内容自足、可独立安装。
> 手法名后括号数字为原书页码，仅供人工溯源——执行时不要尝试去读原书文件。

## 工作流程

### 第 1 步：圈定扫描范围（默认只扫增量改动）

用户**已明确指定目标**（"重构这段代码/这个文件"）时，以用户指定为准，跳过本步。
未指定目标时，默认只扫描"用户自己动过的代码"（营地法则：重构你触碰的地方），不惊动全仓库：

1. 用 git 确定增量范围（相对上游分支，同时涵盖未提交与已提交未推送）：
   ```bash
   git diff --name-only @{u}                  # 增量文件清单（工作区 vs 上游）
   git ls-files --others --exclude-standard   # 未跟踪的新文件
   git log --oneline @{u}..HEAD               # 增量提交清单（简报用）
   ```
   无上游分支时退回 `git diff --name-only origin/main`（或 `origin/master`）。
2. 向用户**简报范围**：本次覆盖了哪几个提交、哪些文件。
3. 后续的坏味道诊断与重构默认只针对该范围进行。
4. 每次报告完增量扫描/重构结果后，**主动提醒**："本次仅覆盖你的增量改动，如需全仓库坏味道扫描请告知。"（全仓库扫描应分模块进行，避免一次铺开过大。）

**例外处理**：
- 非 git 仓库：无法增量定位，请用户指定文件/目录，或征得同意后全仓库扫描。
- 工作区干净且无未推送提交：没有增量可扫，直接询问是否做全仓库扫描。

### 第 2 步：明确意图，建立基线
- 先想清楚**为什么要重构**：预备性重构（为加新特性铺路）？帮助理解（读懂代码并把理解写回代码）？捡垃圾（路过顺手清理）？
- 重构与加功能是**两顶帽子**：绝不混在同一个提交里。
- 通读目标代码，理解它**现在做了什么**（而不是它应该做什么）。
- **安全网**（详见 `references/testing.md`）：
  - 无测试 → 先为现有行为补特征测试（随便填期望值 → 用实际值回填 → 故意引入错误确认会失败 → 恢复）。
  - 有测试 → 先跑一遍确认全绿。
  - 实在无法测试 → 至少明确验证手段（编译、运行样例），且只做低风险手法。

### 第 3 步：诊断坏味道
读取 `references/smells.md`，对照**第 1 步圈定范围内的代码**识别坏味道，选出**最影响理解的一个**先攻击——不要贪多。
记住何时不重构：这段代码不会再被修改；丑代码藏在稳定 API 之下；重写比重构更容易。

### 第 4 步：查阅手法目录
根据坏味道指引读取对应 catalog 文件，按其中的"做法"小步清单执行。
每个手法条目沿用原书五段式：名称 → 速写 → 动机（何时做/何时不做）→ 做法 → 范例。
本 skill 的 catalog 压缩了"动机 + 做法"，**已足以独立支撑执行**；条目中的章号与页码是引用信息（供人工溯源），不是文件路径，不要试图去打开它们。
名录原则：一个重构并非只有一套做法，熟练后可调整；**情况越复杂，步子要越小**。

### 第 5 步：小步执行循环

```
选取一个坏味道 → 查手法要点 → 应用微小改动 → 编译 → 测试 → 提交
```

- 每步绿色就 commit；重构过程中代码行数可能**增加**（包装成本），这是用明确性换简洁性，正常。
- 常见手法链（详见 `references/principles.md`）：
  - 长函数：找注释定位 → 提炼函数 → 改名 → 移除临时变量（以查询取代/内联）→ 需要复用再拆分阶段。
  - 类型码分支散布多处：建类搬计算 → 工厂函数按类型返回子类 → 多态取代条件表达式。
  - 组织不良的一组函数：先内联成一大块，再按更好的边界重新提炼。

### 第 6 步：收尾
- 复查公开接口是否需同步（调用方、文档、已发布接口要保留旧声明并 deprecated）。
- 向用户汇报：识别了哪些坏味道、应用了哪些手法、行为不变的依据（测试结果）、后续建议。
- 若本次走的是默认增量范围，收尾时再次提醒可做全仓库扫描。
- 营地法则：让代码库比来时更健康，但不必追求完美——在"继续重构"与"回去干活"之间平衡。

## 原则速查（详见 references/principles.md）

- **两顶帽子**：重构时不加功能，加功能时不重构；频繁换帽子没关系，但要清楚戴着哪顶。
- **三次法则**：事不过三，三则重构；不要过早抽象（YAGNI）。
- **性能**：先重构后调优；调优靠度量找热点（程序大半时间耗在一小半代码上），不靠臆测。
- **命名是核心产出**：想不出好名字，往往潜藏更深的设计问题。
- **不可变性是防腐剂**：能不可变就不可变；可变数据作用域越小越好。
- **先封装再搬移**：数据没有转发机制，先封装变量把"重组数据"化为"重组函数"。
- 重构由经济利益驱动（开发更快），不是道德洁癖。

## Skill 维护约定

本 skill 由逐章精读《重构（第二版）》提炼而成（ch1~ch12 全部完成）。改进时：
- 修正/增补条目请保持"动机 + 做法"结构和原书页码锚点；
- 与原书冲突时以原书为准，标注章节便于回查（开发仓库的 `knowledgebase/` 有原书全文，仅作校对用）；
- **可移植性约束**：skill 内不得引用本仓库的文件路径（如 `knowledgebase/`）——用户安装时只带走 `skill/` 目录；引用一律只保留章号与页码。
